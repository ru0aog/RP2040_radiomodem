# AGENTS.md — RP2040_radiomodem  
  
Полудуплексный цифровой радиомодем на RP2040. Наследие двух проектов:  
приёмный тракт из RP2040_receiver (ADC+DMA → DDC → децимация → демодуляция),  
передающий из RP2040_beacon (модулятор → дизеринг-DDS на PIO).  
Тракты физически раздельны и никогда не работают одновременно.  
  
## Архитектура  
  
- **Core 0 (приложение)**: CAT/CLI, декодеры + RSID, планировщик, Hayes-модем,  
  file_manager (RAM-диск + MSC + кольцо состояний во flash), датчики, LCD, LED.  
- **Core 1 (реальное время)**: либо RX-конвейер, либо TX-генератор — ядро  
  арендуется через `trx_control`. Плюс `vfo_poll()` (MASH-дизеринг в TX).  
- **Парковка ядер** (`src/trx/core_sync.cpp`): единственный владелец протокола.  
  С Core 1 — `core_sync_park_core0()`, с Core 0 — `core_sync_park_core1()`.  
  Core 0 обслуживает парк-запросы через `core_sync_poll()` — первой строкой  
  `loop()` и внутри `while(!core1_pll_done)` в `setup()`.  
  Core 1 — через `core_sync_core1_poll()` в `loop1()`.  
  IRQ сохраняются/отключаются ДО ACK и восстанавливаются после выхода —  
  исключён уход в XIP через прерывание во время flash-окон и PLL-перестроек.  
- **Захват** (`src/rx/rx_capture.cpp`): ADC0=I (GP26), ADC1=Q (GP27),  
  round-robin, 16-бит переносы в 32-бит слова [15:0]=I, [31:16]=Q.  
  Один DMA-канал + программный пинг-понг буферов в DMA IRQ0 на Core 1,  
  публикация блоков в SPSC-очередь. Буферы статические (DSP-путь живёт  
  до `mem_arena_switch`, пул сбрасывается при `trx_switch`).  
  
## КРИТИЧНО: PRIMASK и межъядерные spinlock  
  
- **PRIMASK — локальное состояние процессорного ядра.**  
  Сохранённое значение PRIMASK принадлежит только тому ядру,  
  которое выполнило `save_and_disable_interrupts()`.  
- **Запрещено хранить сохранённый PRIMASK в общей переменной**  
  (`static`/global), если доступ к ней возможен с Core 0 и Core 1 —  
  ядра перезапишут значение друг друга.  
- **Запрещено восстанавливать чужой PRIMASK.**  
  Пара save/restore должна выполняться на одном ядре; сохранённое  
  состояние должно находиться в локальном контексте вызывающего ядра.  
- **`spin_try_lock_unsafe()` возвращает `bool`** — только факт захвата.  
  Он НЕ отключает прерывания и НЕ возвращает сохранённое состояние IRQ.  
  Нельзя передавать его результат в `spin_unlock()` как saved_irq:  
  `spin_unlock(lock, true)` вызовет `restore_interrupts(1)` →  
  `primask=1` → прерывания ядра глушатся навсегда.  
- Правильная схема try-lock с IRQ:  
  `saved = save_and_disable_interrupts()` → `spin_try_lock()` →  
  при неудаче `restore_interrupts(saved)`; при успехе сохранить `saved`  
  per-core → unlock: сначала `spin_unlock_unsafe()`, потом  
  `restore_interrupts(saved)`. Владение spinlock и владение PRIMASK —  
  разные вещи, не смешивать.  
- При добавлении новых межъядерных блокировок проверять:  
  1. Кто захватывает spinlock.  
  2. На каком ядре отключаются IRQ.  
  3. Где хранится сохранённый PRIMASK.  
  4. На каком ядре выполняется restore.  
  5. Все ли ветви выхода восстанавливают исходное состояние.  
- Симптомы нарушения: `primask=1`, накопление pending IRQ,  
  отсутствие DMA ISR, зависание park-handshake.  
  
### Гонка s_pll_lock_irq (корень зависаний на разгоне)  
  
`core_sync_pll_try_lock()`/`core_sync_pll_unlock()` используют  
`s_pll_lock_irq[2]` — **per-core** массив, хранящий результат  
`save_and_disable_interrupts()` (не результат `spin_try_lock_unsafe()`).  
  
НЕ делать его общим `static uint32_t`. Старая схема с одной переменной:  
Core 1 сохранял свой saved_irq → Core 0 перезаписывал до unlock Core 1 →  
Core 1 восстанавливал чужое значение → `primask` залипал в 1 навсегда →  
DMA IRQ0 на Core 1 умирал → система зависала.  
  
Симптомы были обманчивы: зависание проявлялось только при двух DMA-каналах  
или `chain_to`, что указывало на DMA. Реальная причина — мёртвый IRQ.  
Диагностика: читать `primask` на Core 1 (`mrs %0, primask`), `nvic_hw->ispr`,  
`dma_hw->ch[N].transfer_count`. В `loop1` оставлен одноразовый сторож  
primask (`cpsie i` при залипании) — не удалять.  
  
## Проверенные решения (не откатывать)  
  
1. **Одноканальный DMA + программный пинг-понг в IRQ** — рабочая схема.  
   Решает ту же задачу, что аппаратный ping-pong, но временные  
   характеристики и потери между блоками проверять отдельно.  
   Выбор между аппаратным и программным ping-pong делать по требованиям  
   производительности и измерениям — не как обход проблем с IRQ.  
2. **`s_pll_lock_irq[2]` per-core** в `core_sync.cpp` — обязательно.  
   Хранит результат `save_and_disable_interrupts()` каждого ядра.  
3. **NULL-guard'ы** в `core_sync_pll_try_lock`/`unlock` (`if (!s_pll_lock)`).  
4. **`__not_in_flash_func`** на `loop1`, `rx_dsp_poll`, `trx_poll_core1`,  
   `rx_capture_start`, `rx_dma_irq`, всём пути парковки и PLL — обязательно:  
   во время flash-окон и PLL-перестроек XIP мёртв.  
5. **`irq_set_exclusive_handler` + `irq_set_enabled(DMA_IRQ_0)`** вызываются  
   на Core 1 (в `rx_capture_start`, есть `assert(get_core_num()==1)`) —  
   NVIC и таблица векторов у каждого ядра свои.  
6. **`rx_pipeline_set_freq(freq)` перед `rx_pipeline_start()`** в  
   `trx_poll_core1()` — без этого `s_freq_hz` остаётся 0 и на возврате  
   TX→RX получаем `[RX] start f=0`, NCO уезжает.  
7. **RSID кормится только в SSB-ветке демодулятора**: `rsid_resampler_push(m)`  
   стоит внутри `else` (не RAW). При `RXD_DEMOD_RAW` RSID молчит —  
   нужен `rx_dsp_set_demod(RXD_DEMOD_USB)` после `rx_dsp_start()`.  
8. **`rsid_poll()` обязателен в `loop()`** — без него детект не печатается  
   и не применяется (`rx_decoders_on_rsid` не вызывается).  

### Инженерный принцип: цена страховок  
  
Не всякая потенциальная страховка улучшает надёжность. В критическом  
коде RP2040 (PLL-окна, IRQ, межъядерные протоколы) лишнее состояние  
и дополнительные ветви тоже имеют цену:  
  
- Каждый `static`/флаг — это состояние, которое нужно держать  
  согласованным между ядрами и которое само может залипнуть или  
  рассинхронизироваться. Пример: `s_pll_lock_irq` был «страховкой»  
  для корректного restore — и стал корнем зависаний, потому что  
  оказался общим для двух ядер.  
- Каждая диагностическая ветвь в горячем пути (`loop1`, IRQ,  
  park-протокол) меняет тайминги и может маскировать или создавать  
  гонки. Диагностику добавлять точечно и убирать после локализации.  
- Страховка оправдана, только если она: (а) проверяет инвариант,  
  который реально может нарушиться, и (б) сама не вводит нового  
  разделяемого состояния. Сторож `primask` в `loop1` проходит оба  
  критерия (одноразовый, локальный, без ветвей в горячем пути);  
  флаг `s_pll_lock_held` — нет (дублирует состояние, которое уже  
  гарантируется парностью вызовов).  
- Правило: сначала корректный протокол (парность lock/unlock,  
  per-core состояние), потом — минимум страховок поверх, а не  
  вместо него.
  
## Разгон (проверено стабильно)  
  
- Номинал 133 МГц → рабочая точка **373.3 МГц** (скан quad_vfo выбрал  
  fbdiv=280, postdiv 3/3, VCO 3360 МГц — формально вне спека PLL 750–1600 МГц,  
  работает на данном чипе; на другом экземпляре может не взять).  
- Потолок: `pll_ceiling = {95, 3, 1, 380000000}` (VCO 1140 МГц, в спеке),  
  `vfo_max_clk_sys_hz = 380000000`, `vfo_max_pll_vco_hz = 4200000000`,  
  VREG 1.30V. SET.TXT `MAX_CLK_SYS` на диске перекрывает кодовый потолок —  
  при смене потолка править и файл на диске.  
- Нагрузка на 373 МГц: `dsp=347‰`, `total=705‰` — запас ~30%.  
- `clk_sys` в статус-строке показывает кэш 133 МГц — косметика, не баг.  
  
### Подтверждение стабильности разгона  
  
- Коммит `0845e9a` — исправлена гонка `s_pll_lock_irq`.  
- Первопричина зависаний — межъядерное смешивание сохранённых  
  значений PRIMASK, а не ограничение DMA или `chain_to`.  
- После исправления восстановлена работа разгона от 133 до 373 МГц.  
- Максимальная проверенная рабочая точка: около 373,3 МГц.  
- Результат относится к испытанной плате и конфигурации.  
  Не считать его гарантированной рабочей частотой любого RP2040.  
  
## КРИТИЧНО: flash-запись и Core 1  
  
- `save_state()`/`log_append()`/`do_flash_erase`/`do_flash_program` — только  
  при `trx_state()==TRX_RX` и только с парковкой Core 1 через  
  `core_sync_park_core1()` → `save_and_disable_interrupts()` →  
  `flash_range_erase/program` → `flash_flush_cache()` → unpark.  
  Все функции пути — `__not_in_flash_func`. Одна парковка на весь цикл  
  erase + program слота (`file_manager.cpp:533`).  
- **Сохраняется и восстанавливается именно локальное состояние IRQ  
  Core 0** (ядро, исполняющее flash-операцию); Core 1 к этому моменту  
  уже припаркован. Не смешивать с чужим PRIMASK — см. раздел  
  «PRIMASK и межъядерные spinlock».  
- `flash_safe_execute()`/`multicore_lockout`/`rp2040.idleOtherCore()` —  
  НЕ использовать: не согласованы с core_sync-протоколом, проверенные  
  зависания. Парковка — только `core_sync_park_core1()`.  
- `file_manager_set_flash_safe_ready(true)` — в `setup()` на Core 0 после  
  `while(!core1_pll_done)` (сеттер работает только на Core 0 — внутри  
  проверка `get_core_num()`). Без него `flash_write_allowed()` молча  
  блокирует `save_state`.  
- В boot flash не стирается: `init_file_manager()` только читает XIP и  
  строит RAM-диск. Первая запись — через `state_save_pending` из  
  `check_and_handle_pc_changes()` при живой системе. Erase в setup() при  
  работающем Core 1 = кирпич (XIP мёртв во время erase/program).  
- `init_file_manager()` вызывать в setup() ДО `core0_ready = true`:  
  в этот момент Core 1 стоит в `while(!core0_ready)` и обращения к flash  
  безопасны.  
  
## КРИТИЧНО: порядок USB-инициализации (корень «USB-устройство не опознано»)  
  
`TinyUSBDevice.begin()` вызывается ТОЛЬКО один раз — внутри `usb_audio_init()`  
(маунт стека). Все `*.begin()` интерфейсов — регистрация в списке Adafruit  
TinyUSB, обязаны отработать ДО старта стека:  
  
    init_usb_msc_interface();   // MSC — ПЕРВЫМ  
    init_file_manager();  
    usb_audio_init();           // UAC (внутри TinyUSBDevice.begin)  
    Serial.begin(115200);       // CDC — последним  
  
Обратный порядок или повторный `usb_msc.begin()` = дескрипторы меняются  
на лету в окне энумерации → «USB-устройство не опознано», пропадают  
COM+UAC+MSC целиком. После `begin()` обязателен `usb_msc.setUnitReady(true)`.  
`remount_usb_disk()` защищён флагом `usb_started` — `setUnitReady()` до  
`usb_msc.begin()` не вызывать.  
  
## КРИТИЧНО: цепочка записи Windows → flash  
  
Windows → `msc_write_cb` (пишет в ram_disk_buffer, ставит  
`pc_activity_detected`, `pc_written_regions`, `last_msc_write_time`)  
→ `check_and_handle_pc_changes()` в `loop()` (ждёт 1.5 с тишины,  
проверяет `flash_write_allowed()` и `trx_state()==TRX_RX`)  
→ `save_state()` (весь RAM-диск → ring-слот, SlotMeta+CRC32)  
→ парсеры по битам регионов (0x02 INFO / 0x04 CONFIG / 0x08 SET)  
→ `remount_usb_disk()`.  
  
Обязательные условия, без которых цепочка молча обрывается:  
1. `file_manager_set_flash_safe_ready(true)` в `setup()` после  
   `while(!core1_pll_done)` — без него `flash_write_allowed()` всегда false.  
2. `check_and_handle_pc_changes()` — каждый проход `loop()` на Core 0.  
3. `msc_flush_cb` НЕ должен обновлять `last_msc_write_time` — Windows  
   шлёт SYNCHRONIZE CACHE постоянно, иначе окно 1500 мс не наступит  
   никогда. Flush ставит только `pc_activity_detected`.  
4. Гейт `pc_written_regions == 0` обязателен: пустые flush без записей не  
   должны гонять erase+program 32 КБ (износ flash).  
5. LOG.TXT (lba >= RAM_SECTORS) — read-only для ПК: `msc_write_cb`  
   возвращает `bufsize` (фейковый успех), не -1 — Windows на ошибке  
   сектора рвёт всю транзакцию и ретраит бесконечно. Пишется только  
   изнутри через `log_append()`.  
  
## Core 1 никогда не блокируется  
  
Никаких Serial.printf/delay/mutex/multicore_fifo на Core 1 — ни в init,  
ни в DSP, ни в VFO. Core 0 регулярно паркуется в RAM-ожидании и не  
обслуживает USB FIFO → любой printf с Core 1 висит на полном буфере →  
deadlock. Диагностика с Core 1 — только volatile-поля, печатает Core 0.  
Это была причина минимум трёх «зависаний» с разными симптомами.  
(Исключение-нарушение: отладочные `Serial.println` в `rx_capture_start` —  
маркеры m1-m11, подлежат удалению.)  
  
## CAT/CLI — общий CDC-порт  
  
- `cat_poll()` (`src/cat/cat.cpp`) — единственный читатель `Serial`.  
  Демультиплексор: байты до `;` → CAT-буфер → `cat_execute()`;  
  строка до `\n` с непустым буфером → `cli_execute()` (`src/cat/cli.cpp`).  
  `\r` игнорируется. CAT-команды без `;` уйдут в CLI — это осознанно.  
- CLI — порт `check_serial_commands()` из RP2040_beacon: help, status,  
  setparam, rx/quad/vfo/mem/limits, clear log, format disk, remount, reset,  
  tx. Команды без аналога — заглушки "[CLI] '<cmd>' не поддерживается".  
- Демодулятор задаётся `uint8_t` + макросы `RXD_DEMOD_*` (rx_dsp.h),  
  enum `DemodMode` НЕ существует — не использовать.  
  
## TX по команде из COM-порта  
  
- `src/trx/tx_job.{h,cpp}` — заявка: `tx_job_submit(mode, freq, payload)`  
  ставит, `tx_job_poll()` в `loop()` исполняет:  
  QUEUED → `trx_switch(TRX_TX)` → ACTIVE → `mi->tx_frame()` (блокирующий,  
  как `send_*_string` в маяке) → гарантированный `trx_switch(TRX_RX)`.  
- Abort: `pc_file_written` или `tx_job_abort()` → TXJ_ABORTED.  
  Для реального прерывания в посимвольном цикле моды нужна проверка  
  `tx_job_state()==TXJ_ABORTED` (аналог `mfsk_abort()` маяка).  
- `tx_frame` принимает `const uint8_t*` — каст от `char*` обязателен.  
- PTT-выхода нет — только `PIN_PTT_LED` (GP25).  
  
## Файловая система (src/filesys/file_manager.cpp)  
  
- **Диск — эмуляция, не ФС.** `msc_read_cb`/`msc_write_cb` обслуживают LBA;  
  RAM-буфер покрывает только служебные сектора + INFO/CONFIG/SET.  
- **Геометрия**: FAT12, кластер=1 сектор, 566 секторов: boot(0), FAT(1-2),  
  каталог(3-5), INFO(6-21), CONFIG(22-37), SET(38-53), LOG(54-565).  
  RAM-буфер = 54 сектора (27 КБ).  
- **LOG.TXT** (256 КБ) виртуальный — читается хостом напрямую из XIP по  
  `LOG_FLASH_OFFSET = 0x140000`, RAM не занимает. Append 256-Б страницами,  
  erase 4-КБ блоками по кругу; указатель в SlotMeta + boot-восстановление  
  сканом первого 0xFF-байта. После порции записи — `remount_usb_disk()`  
  (Windows кэширует FAT и данные).  
- **Кольцо состояний**: 8 слотов × 32 КБ @ 0x180000-0x200000.  
  Слот = INFO 8КБ + CONFIG 8КБ + SET 8КБ + RESERVED 7.5КБ + SlotMeta 512Б  
  (magic, seq, CRC32, log_write_ptr). Запись = новый слот seq+1, boot берёт  
  max seq с валидными magic+CRC, сравнение seq wrap-aware.  
  Кольцо — для износа flash, не для отката.  
- **Flash-карта**: прошивка < 0x140000 (запас большой, проверять по  
  firmware.map при росте).  
- **SET.TXT** — файл скрытых данных (scan-таблица, MAX_CLK_SYS, MAX_PLL_VCO,  
  XOSC_PPB). CONFIG.TXT — бывший SET.TXT (переименован).  
  
## SET.TXT → переменные разгона  
  
- Парсер пишет в `vfo_max_clk_sys_hz` / `vfo_max_pll_vco_hz`  
  (weak-дефолты в `src/vfo/vfo.cpp`, extern в `vfo.h`)  
  и `vfo_xosc_corr_ppb`.  
- Значения применяются в `quad_fill_cfg()` при `vfo_init()` — правка  
  SET.TXT с ПК вступает в силу только после ребута (переинициализации  
  VFO нет).  
- ВНИМАНИЕ: `clk_sys_min_hz` в `quad_fill_cfg()` должен быть ≤  
  `vfo_max_clk_sys_hz`. Пустой диапазон (min > max) → PLL-сканер не  
  находит конфигурацию → `vfo_on_trx_switch()` не возвращается →  
  зависание в `while(!core1_pll_done)`.  
  
## Парковка ядер и перестройка PLL  
  
При диагностике зависаний разделять две группы причин:  
  
1. **Ошибки протокола парковки**: stale-ack, неправильный порядок req/ack,  
   отсутствие `__sev()`, отсутствие обслуживания `core_sync_poll()`.  
2. **Ошибки локального состояния IRQ**: некорректное сохранение/  
   восстановление PRIMASK, в том числе гонка `s_pll_lock_irq` между  
   Core 0 и Core 1.  
  
Обе группы способны приводить к зависанию PLL-перестройки  
и межъядерного handshake.  
  
Зависания при переключении `clk_sys` в `quad_vfo_set_clk_sys()`  
(src/vfo/quad_vfo/quad_vfo_pll.cpp):  
  
1. **Парковка Core 0 обязательна** — без неё Core 0 исполняет flash-код  
   и обращается к XIP в момент переключения шины.  
2. **`rp2040.idleOtherCore()` ненадёжен в рантайме** — handshake виснет,  
   когда на Core 0 активен TinyUSB/CDC. Заменён флаг-протоколом core_sync.  
3. **Флаг-протокол**: Core 1 взводит req и ждёт ack; Core 0 в  
   `core0_wait_in_ram()` (`__not_in_flash_func`) подтверждает на каждой  
   итерации, `__wfe()` между проверками; unpark: `req=0; __dmb(); __sev();`  
   — без `__sev()` `__wfe()` не просыпается. Core 0 обслуживает  
   `core_sync_poll()` в обоих циклах ожидания: `while(!core1_pll_done)`  
   и `trx_switch`.  
4. **Stale-ack — реальная гонка**: ack гасится перед взводом req, иначе  
   следующий park проходит мимо и шина переключается под живым Core 0.  
5. **Никакого Serial/printf/flush внутри парковочных окон** — CDC  
   обслуживается Core 0, при припаркованном ядре вывод в порт = дедлок.  
   Диагностика внутри окон — только SRAM-счётчики, печать после unpark.  
6. **`ssi_hw->baudr` перед `clk_sys_to_pll`** — при переходе на высокий  
   clk_sys XIP без замедления делителя убивает обращение к flash.  
   Делитель ставится до переключения mux (сейчас baudr=4; при глитчах  
   поднять до 6). Нужен во всех местах: основной путь, ретрай, rollback.  
7. **Mux clk_sys — регистрами, без `clock_configure`** — SDK-обёртка  
   тянет flash-код. Свой путь: сначала `src=0` (ref) + ждать `selected&1`,  
   потом `auxsrc=clk_sys_pll`, потом `src=1` + ждать `selected&2`.  
   Менять `auxsrc` под выбранным aux нельзя — глитч.  
8. **В момент PLL-парковки на Core 0 — пустой цикл ожидания** без живого  
   TinyUSB-стека: USB-инит (usb_audio_init и т.п.) выполняется после  
   `while(!core1_pll_done)`. Реэнумерация detach/attach отключена —  
   полураспавшийся дескриптор давал «Неизвестное USB-устройство».  
9. **Диагностика, которую держать в коде**: PARK TIMEOUT-дамп  
   (req/ack/enter/exit/loop_seen/dbg_stage) вместо вечного спина;  
   LED-маячок 2 Гц в `loop()` (замёрз = ядро умерло); маркеры `[PLL] dbg:`  
   на границах сегментов.  
10. **Остаточный риск**: если Core 1 зависнет, держа req, Core 0 заснёт  
    в `core0_wait_in_ram` навсегда. Для релиза — второй таймаут внутри  
    RAM-цикла. Аналогично `while(!core1_pll_done)` в setup() сейчас без  
    таймаута — стоит добавить (10 с → `[ERR]` + живой USB).  
  
## quad_vfo: проверенные решения и ловушки  
  
### Верификация PLL — только измерением, не LOCK-битом  
  
- `quad_vfo_set_clk_sys()` подтверждает захват связкой «аппаратный LOCK +  
  измерение clk_sys счётчиком FC0 в окне ±0,3%», до 3 попыток с полным  
  циклом `clk_sys→XOSC→PLL`. LOCK-бит сам по себе недостаточен — на  
  оверклоке VCO он может врать.  
- Протокол возврата трёх состояний через `out_nominal_ok`: цель  
  подтверждена / цель не взяла, но номинал восстановлен и измерен /  
  шина на XOSC (полный отказ). `quad_vfo_start` при «номинал  
  восстановлен» НЕ останавливает генератор — пересчитывает делитель  
  под фактический clk_sys (`recompute_div`).  
- `rollback_nominal` возвращает `bool` — результат отката тоже  
  верифицируется измерением.  
  
### FC0 (frequency counter) — не читать result вручную  
  
- Прямая запись `fc0.interval`/`fc0.src` и чтение `fc0.result` давала  
  мусор ~+8 МГц → верификация валилась → rollback → генерация пропадала.  
  Рабочий вариант: `frequency_count_khz(src) * 1000u` — квантование  
  ±1 кГц, для окна ±0,3% достаточно. «Герцового» разрешения на FC0 нет.  
- `measured` vs `cached` расходятся на ±1 кГц — квантование счётчика,  
  не ошибка PLL.  
  
### Сканер PLL  
  
- `refdiv` перебирается 1..3 — НЕ ограничивать до 1: refdiv=2/3 даёт  
  более мелкую решётку clk_sys и меньшую остаточную ошибку LO.  
- `pll_vco_max_hz` в конфиге — пользовательский потолок, может превышать  
  даташитные 1600 МГц (проверено до 4,2 ГГц, VCO 3,36 ГГц лочился).  
  Валидация только снизу (>= 400 МГц). Профили `pll_nominal`/`pll_ceiling`  
  обязаны оставаться в спеке.  
- `p1 < 2` в профиле молча подменяется номиналом — недокументированное  
  деление пополам на VCO < ~2,8 ГГц.  
- Остаточная ошибка LO ~600–2500 Гц — дискретность решётки VCO, не баг.  
  В точном режиме (nco_max_hz=0) возможен err=0.  
  
### Электрический предел LO — 45 МГц  
  
- `QUAD_VFO_LO_MAX_HZ = 45000000` — выше ~45–50 МГц GPIO-пэды заваливают  
  фронты: квадратура вырождается в синус с потерей амплитуды  
  (осциллограммы: 14 МГц чисто, 28 МГц скругление, 51 МГц — синус 3,4Vpp).  
  Надёжная квадратура — до ~30 МГц.  
- Проверка по `lo_hz` (не `freq_hz`) — ПЧ-режим с freq чуть выше предела  
  допустим, если LO в пределе.  
  
### Тихий режим  
  
- `quad_vfo_set_quiet(bool)` + `quad_vfo_pll_set_quiet(bool)` глушат весь  
  вывод [QUAD]/[PLL] — нужен при перестройке энкодером (каждый детент =  
  полный цикл stop→scan→PLL→start). Все Serial в обоих .cpp завёрнуты в  
  `QV_LOG`/`QP_LOG` — при добавлении printf использовать макросы.  
- `quad_vfo_debug()` тоже подавляется флагом (несовпадение с документацией  
  в заголовке — известный хвост).  
  
### Энкодер (порт из RP2040_beacon)  
  
- Пины маяка: ENC_A=GP20, ENC_B=GP21, BTN=GP19.  
- `enc_lut` + `enc_pending_steps` + `ENC_TICKS_PER_DETENT=4` — накапливать  
  тики, отдавать только полные детенты; иначе один щелчок даёт несколько  
  шагов. Ускорение — в poll по dt, не в ISR.  
- Кнопка — опрос с дебаунсом 30 мс, не IRQ (дребезг даёт ложные  
  прерывания).  
  
## Регрессионный тест  
  
Обязателен после любых изменений в `quad_vfo_pll.cpp`, `core_sync.cpp`  
и `rx_capture.cpp`:  
  
| Тест | Что проверяем |  
|------|---------------|  
| 133 МГц | Базовая работоспособность |  
| 143,5 МГц | Работа IRQ и DMA после разгона |  
| 373,3 МГц | Верхняя проверенная рабочая точка |  
| DMA A↔B + chain | Аппаратный ping-pong |  
| DMA IRQ на Core 1 | Регулярный вход в ISR (`cap_isr` растёт) |  
| PRIMASK после try_lock/unlock | На обоих ядрах возвращается к исходному значению после каждого захвата и освобождения spinlock |  
| RX → TX → RX | Переключение режимов и восстановление частоты |  
| Park / unpark | Повторные межъядерные handshake |  
| Flash save | Запись состояния при работающем USB и корректной парковке |  
  
В диагностике держать: PRIMASK обоих ядер (читать непосредственно на  
соответствующем ядре — `mrs %0, primask`), счётчик DMA IRQ (`cap_isr`),  
счётчики park/unpark (`core_sync_get_stats`).  
  
## Тупиковые пути (проверено — не повторять)  
  
- Два DMA-канала + `chain_to` A↔B не являются причиной зависаний.  
  Первопричина — гонка PRIMASK в `core_sync.cpp`/`quad_vfo_pll.cpp`.  
  При `primask=1` Core 1 не обслуживает DMA IRQ независимо  
  от конфигурации DMA.  
- Не использовать отказ от аппаратного chaining как обходной путь  
  для проблем с IRQ. Выбор между аппаратным и программным ping-pong  
  делать по требованиям производительности и измерениям.  
- Перенос DMA IRQ на Core 0 — не требуется, IRQ на Core 1 работает.  
- `flash_safe_execute()` / `multicore_lockout` / `rp2040.idleOtherCore()`  
  для flash-окон — не согласованы с core_sync, проверенные зависания.  
- `__get_PRIMASK`/`__enable_irq` — CMSIS-интринсики недоступны в тулчейне,  
  использовать `__asm volatile ("mrs %0, primask" ...)` / `cpsie i`.  
- `nvic_hw->iser` — одиночный регистр, не массив (без `[0]`).  
- `extern bool clk_boosted` без `volatile` — конфликт с soft_tx.h,  
  volatile часть типа.  
- Дубли определений pin_freq_out/subband_pins/vfo_max_*/vfo_xosc_corr_ppb  
  в file_manager.cpp — владельцы: pins.cpp, soft_tx.cpp, vfo.cpp.  
  В file_manager только extern через заголовки.  
- `"строка" + BCN_VER` — BCN_VER макрос-литерал, нужен String(BCN_VER).  
- rtc_* переменные и get_current_date/time — в радиомодеме нет RTC,  
  живут как weak-заглушки в fmgr_stubs.cpp.  
- Уменьшение RAM-диска «только размером» невозможно: геометрия FAT12  
  (кластерные константы, BPB, цепочки FAT) пересчитывается целиком.  
- Повторный `usb_msc.begin()`/`init_usb_msc_interface()` после маунта —  
  вешает USB целиком (COM+UAC+MSC пропадают).  
  
## Известные хвосты  
  
- `dbg_l1`/`dbg_poll_in`/`dbg_poll_out` в `.ino` — мёртвые счётчики,  
  нигде не инкрементятся (l1/pin/pout в sync-строке всегда 0 — это норма).  
- Маркеры `m1`-`m11` и `Serial` в `rx_capture_start` — отладочные, чистить.  
- `dma_overclock_test` — мёртвый код.  
- SET.TXT `MAX_CLK_SYS` молча перекрывает потолок с диска — источник  
  «не применяется разгон».  
- `arena watermark: 0/36864` — TRX-пул в RX не используется (или  
  watermark не обновляется). Если реальный ноль — пул можно урезать.  
- `aud_fill=0`/`aud_drop=0` — UAC-аудио на хосте ещё не проверено;  
  при щелчках смотреть частоту `usb_audio_poll()`.  
- Дубли в логе (`[RX] dsp init`, `[DEC] init`, `[MSC] registering`) —  
  двойные вызовы init, не критично.  
- `cap_isr` — счётчик DMA IRQ0 (~488/с при Fs=250k, блок 512 пар),  
  не ошибки.  
- RAM ~94.5% занято — `ram_disk_buffer` 27 КБ; рост .bss уронит линковку  
  (location counter backwards) или стек. При нехватке: ужать  
  LOG_CLUSTERS или MEM_TRX_POOL_SIZE.  
- Цикл RX→TX→RX при активной JTTY (перевыделение арены) не тестирован.  
- Частота приёма зашита в нескольких точках `.ino` (trx_switch возврата,  
  vfo_on_trx_switch, cat_set_freq_hz, rx_dsp_start) — при смене править все.  
- PLL-расхождение: clk_sys отличается от целевого на единицы кГц,  
  LO err −355…+3500 Гц — дискретность решётки, не баг.


### TODO: проверить RSID после введения кванта DSP (c208765)  
  
**Контекст.** В `rx_dsp_poll` (`src/rx/rx_dsp.cpp`) введены два  
ограничения:  
  
1. **Квант DSP** — не более `DSP_MAX_BLOCKS_PER_POLL = 2` блоков  
   за проход `loop1` (ранее цикл выкачивал очередь до конца и мог  
   задержать `core_sync_core1_poll`/`trx_poll_core1` на ~6 мс).  
2. **RSID по таймеру** — `rsid_rx_service_sliced()` вызывается  
   каждые `RSID_SLICE_US = 2000` мкс независимо от состояния  
   очереди (ранее — только когда очередь пуста, `!got`).  
  
**Наблюдаемый эффект.** Нагрузка `rsid` в пульс-строке упала  
с ~430‰ до ~73‰: RSID больше не получает «всё свободное время»,  
а только гарантированный срез. `dsp` ≈ 264‰, `total` ≈ 340‰,  
`cap_isr` растёт, `drop=0` — захват и DSP в норме.  
  
**Что проверить при первой возможности.**  
- Детектируется ли RSID на живом сигнале (слабом, с QSB).  
- Если детект деградировал — варианты по возрастанию квоты:  
  a) `RSID_SLICE_US` 2000 → 1000/500 мкс;  
  b) несколько вызовов сервиса за срез (если итеративный);  
  c) гибрид: таймер-срез + вызов при пустой очереди (как было),  
     но с сохранением кванта DSP.  
- Критерий приёмки: RSID-детект не хуже, чем до c208765,  
  при `drop=0` и `qfull=0` в статистике захвата.

При проверке RSID полезно сравнить с базой: откат на 5b0a017 (до кванта) даст эталонное поведение детекта.
